# Starsector Refit Viewer

A static, dependency-free web app that recreates the core of Starsector's refit
screen in the browser: pick any vanilla hull, see its weapon slots and firing
arcs over the ship sprite (or a schematic), fit weapons under the game's
legality rules, and watch ordnance points and flux update live. Installed
hullmods change the ship's effective stats and every weapon's effective range
live, exactly as parsed from the game's own hullmod scripts. Builds can be
saved in the browser and exported as real game `.variant` files — or import an
existing `.variant` to inspect it.

**Unofficial fan project — Starsector © Fractal Softworks. Not affiliated with
or endorsed by Fractal Softworks. All game data and art belong to their

## Running it

No build step. Any static host works (GitHub Pages, a plain web server, etc.):

```
python3 -m http.server 8000   # then open http://localhost:8000
```

Opening `index.html` directly from `file://` mostly works, but Chrome blocks
`fetch()` of local files, so the app will ask you to pick `data.json` manually
via a file dialog. Serving over HTTP avoids that.

## How the data is stored (and why)

The repo is published through a mechanism that only accepts UTF-8 **text**
files — no binary PNGs. So sprites are embedded as base64 data URIs in small
JSON shards and loaded lazily:

- `data.json` — all ship/weapon/hullmod/wing data (see below), generated by `build_data.py`.
- `sprites/ships/<hullId>.json` → `{"sprite": "data:image/png;base64,..."}`
- `sprites/weapons/<weaponId>.json` → `{"turret": ..., "hardpoint": ...}`
- `sprites/hullmods/<hullmodId>.json` → `{"icon": ...}` (icon path taken from the `sprite` column of `hull_mods.csv`, verified against the files on disk)

`data.json` stores only shard *keys* (`"sprite": "ships/onslaught"`). The app
fetches a shard when a ship is selected or a weapon is fitted, caches it in
memory, and fails soft: a missing shard (404 or `file://`) just means no
picture — the ship is drawn as a schematic and the weapon as a colored marker.

## Data provenance

`build_data.py` parses a legally owned copy of **Starsector 0.98a-RC8**:

- `data/hulls/ship_data.csv` — ship stats (deployment points, ordnance points,
  flux, armor, …).
- `data/hulls/*.ship` — hull geometry: slots (type/size/mount/position/arc),
  built-in weapons/mods/wings, sprite name, center, collision radius.
- `data/hulls/skins/*.skin` — skins become extra ship entries layered on their
  base hull (base geometry, skin sprite, skin stat overrides such as the XIV
  hulls' extra ordnance points).
- `data/weapons/weapon_data.csv` — weapon stats. Note its `type` column is the
  **damage** type (KINETIC, HIGH_EXPLOSIVE, …); the **mount** type comes from
  `data/weapons/*.wpn` (`type`/`size` there).
- `data/hullmods/hull_mods.csv` — hullmods: per-hull-size OP costs
  (`cost_frigate`/`cost_dest`/`cost_cruiser`/`cost_capital`), `desc`/`short`
  texts, `hidden`/`hiddenEverywhere` flags, tags, and the icon `sprite` path.
- `data/hullmods/*.java` — the hullmod **scripts that ship as source**.
  `build_data.py` statically parses their `MutableShipStatsAPI` calls into a
  per-hullmod `effects` table in `data.json` (see “Hullmod effects” below),
  and parses `isApplicableToShip` for mutual exclusions and hull-size limits.
  Scripts that live in the game jar (`com.fs.starfarer.api.impl.hullmods.*`)
  have no local source and are not parsed.
- `data/strings/descriptions.csv` — weapon description text (`WEAPON` rows,
  `text1`) and, via `weapon_data.csv`'s `primaryRoleStr`, each weapon's role
  string; both are shown on the weapon spec cards.
- `data/hulls/wing_data.csv` — fighter wings (`id`, `variant`, `op cost`,
  `num`, `tier`, `rarity`, role). The CSV has no display-name column; wing
  names in the viewer are derived from the wing id
  (`mining_drone_wing` → “Mining Drone”), matching the vanilla LPC names.
- Starsector's JSON dialect needs a lenient parser: `//`, `/* */` **and** `#`
  comments, `;` used as a separator, bare enum words (`[RENDER_BARREL_BELOW]`),
  leading-dot floats (`.67`), and trailing commas are all handled.

Regenerate with `python3 build_data.py` (edit `SRC` at the top to point at an
assets tree).

## Coordinate and arc conventions

Slots are stored in `data.json` in **game coordinates**: `x` = forward axis,
`y` = lateral axis, both relative to the ship center, in sprite-pixel units.
The `.ship` `center` is measured from the sprite's **bottom-left**, so the
screen mapping (bow up) is:

```
img_x = center_x + slot.y
img_y = (spriteHeight - center_y) - slot.x
```

**Arc direction** — a slot `angle` maps to the screen direction
`(sin a, −cos a)`: compass-style, positive angles rotate clockwise on screen,
0° = straight at the bow. This was derived empirically, not assumed:

- **Conquest**: every slot on the +lateral side carries a positive angle and
  its mirror twin on the −lateral side carries the exact negative (e.g. the
  broadside turrets at lateral ±42 are angled ±90°, the bow turrets at ±71 are
  ±90°, stern pair at lateral +53/−53 are 160°/200°≡−160°). Positive angles
  therefore tip toward the +lateral (screen-right) side — clockwise on screen.
- **Odyssey** confirms it: its port-side rear slots use angles like 250° and
  260°, which under `(sin a, −cos a)` point aft-and-slightly-port — outward,
  as fitted. Under the opposite sign convention they would point into the hull.
- **Legion**: rear starboard PD at angle 90° points screen-right (starboard),
  its port twin at −90° points screen-left.

For ships without a local sprite, the app falls back to a schematic: the same
game-coordinate math plotted against the `.ship` width/height with the
collision radius shown as a dashed circle.

## Rules implemented

- **Weapon legality**: weapon size ≤ slot size, and mount-type matrix —
  BALLISTIC←ballistic, ENERGY←energy, MISSILE←missile,
  HYBRID←ballistic/energy, COMPOSITE←ballistic/missile,
  SYNERGY←energy/missile, UNIVERSAL←any. DECORATIVE / BUILT_IN / SYSTEM /
  LAUNCH_BAY / STATION_MODULE slots are not fittable. Built-in weapons are
  pre-fitted and locked, and cost no OP.
- **OP accounting**: fitted weapons + hullmods + fitted fighter wings + vents
  + capacitors (1 OP each, max 30); the bar turns red over budget. Built-in
  weapons, hullmods and wings cost no OP.
- **Hullmod picker**: `hiddenEverywhere` mods are excluded and `hidden` mods
  appear only when built into (or already installed on) the selected hull —
  mirroring what the game lets you see. Built-ins are pre-checked and locked.
- **Fighters**: one wing dropdown per launch bay (bay count from the hull's
  LAUNCH_BAY slots, falling back to the `fighter bays` stat). Fitted wings
  export in bay order, built-ins included so bay alignment survives a round
  trip; imports map wings back positionally and re-lock built-in bays.
- **Flux**: weapon flux/sec summed from the data; effective dissipation =
  base + 10/vent; capacity = base + 100/capacitor. Weapons whose CSV flux/sec
  is blank (burst weapons) are flagged as an approximate “flux/shot” extra
  instead of being silently dropped.
- **.variant export/import**: exports the game's variant JSON
  (`hullId`, `fluxVents`, `fluxCapacitors`, `hullMods`, one LINKED
  `weaponGroups` entry with the fitted slots, `wings`). Built-in slots are
  omitted from the export because the game derives them from the hull.
  Import accepts game `.variant` files (all weapon groups are flattened) and
  this app's own exports.

## Visual design reference

The stage and pickers follow the game's real refit screen (checked against a
screenshot of the vanilla UI, not committed here):

- Fitted weapons are drawn **at native sprite scale** (1 sprite pixel = 1
  world unit — ship and weapon sprites share the game's pixel scale), rotated
  to the slot facing, with a thin square outline around each fitted weapon.
- Empty slots use the game's vocabulary of shapes: a **ring with a center
  dot** for turrets, a **directional wedge/trapezoid** for hardpoints, a
  **rounded rectangle** for launch bays — colored by slot type and stepping
  with slot size (S/M/L). The stage sits on a subtle blueprint grid.
- Ship and weapon pickers present game-style information: sprite thumbnails
  on ship rows; weapon spec cards with the weapon's art (turret or hardpoint
  art for the selected slot's mount), size/type pips, OP, and a two-column
  stat grid (range, damage, damage type, EMP, flux, ammo, burst, projectile
  speed) plus the weapon's description text where the game provides one.
- The stats panel uses the game's label-above-value arrangement; hullmods sit
  in a right-hand list with icon, name, and OP cost, built-ins greyed at top.
- The stage camera zooms (mouse wheel, 0.08×–5×) and pans (drag), with
  “Fit ship” and “Fit range” buttons; ranges can be drawn for the selected
  slot only or for all fitted weapons.

## Hullmod effects

For every hullmod whose script ships as Java source, `build_data.py` extracts
the stat modifiers the viewer models and emits them as
`hullmods[id].effects`: weapon range split by class (`ballistic`, `energy`,
`missile`, `beam`, plus the PD-only bonuses and Safety Overrides' range
threshold), `fluxCapacity`, `fluxDissipation`, `armor`, and the maneuvering
stats (`maxSpeed`, `acceleration`, `deceleration`, `maxTurnRate`,
`turnAcceleration`). Each modifier is `flat` / `percent` / `mult`, either a
number or keyed by hull size (the targeting units' `mag` maps). Values are
hand-verified against the sources for the range-critical mods (Integrated
Targeting Unit 10/20/40/60%, Dedicated Targeting Core 35/50%, Advanced
Targeting Core +100% with −40% PD range, Advanced Optics +200 beam range,
ECCM ×0.8 missile range, Unstable Injector ×0.85, Safety Overrides' 450
threshold at ×0.25).

The viewer composes a stat the way the game's stats API does —
`(base + Σflat) × (1 + Σpercent/100) × Πmult` — summing the flat/percent/mult
components of every applicable bonus group (mount class, then beam, then PD)
into one application, applies Safety Overrides' threshold last, and shows the
result as **base → effective** in the stats panel and as each weapon's
effective range in its spec card and on the stage. Applicability rules come
from the same sources: mutual exclusions (ITU / DTC / Advanced Targeting Core
/ Distributed Fire Control, Advanced Optics / High Scatter Amplifier, Safety
Overrides / Civilian-grade Hull + Flux Shunt, …) disable the conflicting
checkbox with the reason shown, and hull-size limits (DTC is cruiser/capital
only; Safety Overrides is not installable on capitals) do the same.

Two jar-only mods are hand-encoded from their in-game tooltips:

- **Ballistic Rangefinder** — raises the *base* range of non-PD weapons in
  ballistic slots before percent/mult bonuses: with a large ballistic slot on
  the hull, small slots +200 and medium +100, result capped at 900; otherwise
  small slots +100, capped at 800. (One tooltip nuance is *not* implemented:
  the flavor text suggests hybrid-type weapons interact with the bonus
  differently; the viewer applies the plain rule to all ballistic-slot
  weapons.)
- **High Scatter Amplifier** — beam weapons' base range above 200 is first
  compressed to `200 + (range − 200) × 0.5`.

Not modeled: s-mod (“built-in”) effect branches — the parser strips them, so
every effect is the base hullmod's; D-mods whose effect scales with damage
severity (`CompromisedArmor`, `DegradedEngines`, `FaultyPowerGrid`) are
skipped by the parser because their magnitude is not a static constant; and
effects outside the modeled set (burn level, sensor profile, CR, EW, etc.)
are ignored. Hullmods whose scripts ship only in the game jar have no parsed
effects beyond the two hand-encoded specials above.

## Save import (read-only)

**Import save…** (top bar, or drag-and-drop a save file anywhere on the
page) reads a Starsector `campaign.xml` and shows your actual fleet:
character name, ship count, total DP, fuel/ly, upkeep, cargo capacity,
and fleet burn (the slowest ship's base burn — Augmented Drive Field
and other burn bonuses are not modeled), plus every ship with its real
loadout's OP total against its hull budget. S-mods show at 0 OP; D-mods
cost OP normally. Clicking a ship loads its real build into the refit
editor — permaMods/s-mods locked like built-ins, with an "S" badge —
where all the usual tools apply and the build can be exported as a
`.variant`.

**Read-only guarantee:** the save is parsed locally with `DOMParser`;
nothing is uploaded anywhere, and the app never writes back into a
save. The fleet list is session-only — it is *not* stored; the only
persistence is the pre-existing current-build autosave of whichever
ship you open. Files over ~80 MB prompt a warning before parsing
(late-game saves can be large; the 12.7 MB reference save parses in
~4 s). Hulls from mods that aren't in the viewer's vanilla data are
listed but can't be opened and are excluded from the totals.

The save format is a compact custom serialization, not clean XML —
player-fleet identification, the member/variant field mapping, the
`_default_D` D-hull rule, and validation against a real 113-ship save
are documented in [SAVE_FORMAT.md](SAVE_FORMAT.md).

Also new in this round: the weapon picker has **size filter chips**
(All / Small / Medium / Large) above the weapon list. The chips reflect
the selected slot — sizes too big for the slot are hidden (a SMALL slot
offers only All + Small) — and compose with the search box and sort;
the filter resets to All whenever a different slot is selected.

## Privacy

Everything is client-side. Builds live in `localStorage`
(`ss-refit-builds`, `ss-refit-current`) and never leave the browser.
Imported saves are parsed in memory only and are never stored or
transmitted.

## Known limits

- **Sprites**: 267 of 268 hulls render with their own sprite — base hulls and
  skins alike (the XIV hulls and other skins use their real skin art, not the
  base hull's). The one exception is `dem_drone`, whose sprite file is absent
  from the pulled graphics tree; it renders as a schematic. 148 of 164 weapons
  have turret/hardpoint art; the rest draw as colored markers. (The 8 weapons
  with no `.wpn` file are fighter/flare weapons and were never fittable.)
- **Missing fighter variant**: the wing `hoplon_wing` references a fighter
  variant, `hoplon_Escort`, that is absent from the game install this data
  was pulled from — Hermes flagged the gap when serving the files, and no
  such variant file exists on disk. The wing itself is kept and fully usable
  in the viewer; only its variant definition (which the viewer doesn't use)
  is missing.
- Hullmod *effects* are simulated for the stats listed under “Hullmod
  effects” above; other effects (and s-mod branches) are not — see that
  section for the exact boundaries.
- One weapon group per exported variant (LINKED); per-group autofire modes
  from imported variants are flattened on import.
- The vanilla `heron.ship` data itself contains two slots with the same id
  (`WS 010`); the viewer preserves the data as-is, so those two slots share
  a fitting.
